# 开发工作流

## 1. 开始任务

1. 读取 `ARCHITECTURE.md`、`VERSION.md` 的当前发布段、`CONTINUATION.md` 和 `AGENTS.md`；随后按具体改动只阅读架构文档的相关部分。
2. 以 `CONTINUATION.md` 的“当前未发布改动”和“下一步”为当前事实；旧聊天和 `docs/archive/` 只用于补充背景。
3. 先定位用户提到的页面、功能模块、对应的内容 JSON 和数据规则。只读相关文件与调用链。
4. 用一句话明确本次变更范围；遇到现有未提交改动时先保护它们，不覆盖或混入不相关文件。

## 2. 实施功能

- 一次聚焦一个可验证的功能，做最小必要改动。
- 页面职责放在 HTML；页面专属样式逐步移入 `css/<page>.css`，页面逻辑逐步移入 `js/<page>-page.js`。拆分应随具体功能逐页进行，不集中重写整个网站。
- 通用组件只有两个以上页面确实复用时再抽取；不要为抽象而抽象。
- UI 文案、故事文本、题库、角色资料和平衡数值分别写入各自既有资料源，不在页面脚本里重复硬编码。
- 更改 Firestore 字段时，同步处理读写代码、规则、架构说明；涉及线上 Rules 时要把“代码推送”和“Firebase 发布”作为两步分别汇报。

## 3. 核对与反馈

- 代码级核对：检查改动文件、JSON 解析、脚本语法和 `git diff --check`；根据任务运行相应检查，不扩大到无关测试。
- UI 核对：桌面和平板/手机窄屏都查看。检查实际对齐、溢出、点击目标、悬停/触摸、页面跳转和刷新后状态。
- 如果环境无法模拟已登录页面或设备，说明哪些只能由用户本地/云端确认；不要把静态检查说成浏览器验收。
- 完成后给用户一段自包含摘要：改了什么、涉及文件、是否已发布、用户下一步如何验证。

## 4. Git 与发布

1. 发布前查看 `git status --short`、`git diff --stat` 和完整文件清单。
2. 只 `git add` 本次功能文件及实际依赖。检查未引用的图片草稿、临时文件和秘密信息，不要误提交。
3. 用户明确要求发布后再提交、推送 `main`。记录功能提交号；GitHub Pages 部署可能需要等待。
4. `firestore.rules` 是源码备份；Git push 不会把规则部署到 Firebase Console。

## 5. 交接与上下文控制

- 每完成一个任务，更新 `CONTINUATION.md`：当前分支/提交、工作树未发布改动、已确认行为、待办和本地启动方式。保持约一屏到两屏，优先删除过期事项。
- 每次发布更新 `VERSION.md`；仅当页面职责、Firestore 数据/权限或系统边界变化时更新 `ARCHITECTURE.md`。
- 完成的旧工作记录移入 `docs/archive/`，并注明它是历史资料。当前状态只在主文档维护一份。
- 独立功能使用新的 Codex 对话时，提供仓库路径和当前 `CONTINUATION.md`；无需复制全部聊天记录。
